# Unofficial Custom Build Identity Design

## Goal

Make firmware builds produced by this fork visibly distinct from upstream PedalinoMini releases, especially in installer-facing surfaces, so users do not mistake them for official upstream builds.

The approved build label is:

```text
PedalinoMini 6 T-Display S3 Custom (Unofficial)
```

## Scope

Update build and installer identity surfaces that describe what firmware is being installed:

- `index.html` page title, main heading, footer text, and a short visible notice near board/version selection.
- `README.md` top-of-file disclaimer before the upstream project overview.
- The dynamic ESP Web Tools manifest generated by `index.html`.
- Static manifest templates under `manifest/`.
- Existing generated firmware manifest JSON files under `firmware/`.
- Fork release notes.

## Non-Goals

Do not change runtime connectivity identity by default:

- Do not change default hostnames or `.local` behavior.
- Do not change BLE MIDI names.
- Do not change USB MIDI identity.
- Do not change saved config compatibility or device provisioning behavior.

Those names are user/device-facing connection points, and changing them could cause unnecessary reconnection or discovery surprises. The installer and manifest identity are enough to make the build provenance clear without disrupting live-device workflows.

## Installer Behavior

The installer should clearly present itself as an unofficial custom build installer. The selected board/version workflow remains unchanged:

1. User selects board.
2. User selects version.
3. Installer generates the ESP Web Tools manifest locally.
4. User connects over USB or Bluetooth LE.

The generated manifest `name` should use the approved label so ESP Web Tools also shows the unofficial/custom identity in its install dialog.

## README Behavior

The README should start with a short disclaimer that this repository/build is an unofficial custom fork focused on a PedalinoMini 6-style LilyGO T-Display S3 setup. The disclaimer should keep the upstream project name visible while making the fork status clear before a reader reaches upstream installation or support instructions.

## Manifest Behavior

Generated and template manifests should use the approved label in their `name` field. Firmware paths, versions, offsets, chip families, and erase behavior should remain unchanged.

## Validation

Before committing implementation:

- Run the local config-surface check: `python scripts\validate_config_surfaces.py`.
- Run its unit tests: `python -m unittest scripts.test_validate_config_surfaces`.
- Run `pio run -e lilygo-t-display-s3` because `index.html` and manifests do not compile into firmware, but AGENTS.md names this as the primary target for fork changes.

## Open Decisions

No open naming decision remains. The approved label is fixed for this implementation.
